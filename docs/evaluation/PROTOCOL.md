# ReguMate 三轮泛化评测与反硬编码协议

协议版本：1.0  
适用项目：ReguMate  
执行环境：Windows + PowerShell + Git + Docker + SQLite + Qdrant + DeepSeek API

## 1. 目标与优先级

本项目同时追求：

1. 官方 `data/contest_dataset/QA数据.xlsx` 300题始终保持300/300；
2. 删除现有评测定向硬编码，未来禁止通过硬编码提分；
3. 使用官方500份文档作为唯一语料池，连续完成三批全新100题内部盲测；
4. 建立可复现、可追溯、不会因修改评分器而虚高的评测链路。

优先级：

```text
真实性与无泄漏 > 官方300/300门禁 > 证据可信度 > 新100题分数 > 性能
```

P95只记录，不作为硬门槛。

## 2. 不可变基准

不得为提高成绩而修改：

- `data/contest_dataset/QA数据.xlsx`；
- `data/contest_dataset/dataset/nfra_page_attachments_500/` 中500份官方文档；
- 官方文档manifest、来源和哈希；
- 已冻结轮次的问题、金标哈希、首跑原始输出、评分报告和锁文件。

开始前记录：当前分支、commit、工作区状态、官方QA哈希、500文档语料快照、关键评测脚本哈希、环境摘要。

## 3. 反硬编码规则

### 3.1 禁止

- 根据官方题号、挑战题号、题号前缀分支；
- 完整问题、规范化问题、关键词组合或语义相似度命中特定评测题后返回答案；
- 在生产代码或prompt中保存标准答案、固定监管结论或题目专用数值；
- 根据特定文件名、doc_id、chunk、sheet或cell直接返回预设答案；
- 从QA、questions、gold或历史结果中加载答案给运行时问答；
- 为单个失败case或近似改写增加专用条件；
- 通过放宽评分器、容错或归一化把实质错误判对；
- 使用缓存映射绕过正常RAG链路。

### 3.2 允许

- 通用金融术语、简称、文号、日期、条款号和期间归一化；
- 通用单位换算和同比、环比、占比、差值、求和等确定性公式；
- 通用Word/PDF/Excel解析；
- 多级表头、合并单元格、行列、单位、期间定位；
- BM25、向量、元数据过滤、rerank、父子chunk和跨文档证据聚合；
- 基于实际检索证据的确定性提取和计算；
- 通用引用校验、证据充分性和拒答规则。

### 3.3 判定标准

删除某一道评测题后，该逻辑是否仍是合理、通用、可解释和可复用的系统能力。否则视为硬编码。

## 4. 官方300题质量门禁

使用真实API、完整SQLite/Qdrant索引和500份官方文档运行，不使用mock。

建议优先复用并核查：

- `scripts/upload_contest_knowledge_base.ps1`
- `scripts/run_contest_qa_test.ps1`
- `scripts/run_contest_qa_test.py`
- `scripts/evaluate_contest_qa.py`

运行节点：

- 任务开始基线；
- 删除硬编码后；
- 解析、检索、表格、公式、推理或生成链路的大修改后；
- 每轮优化完成后；
- 每个有效提交前；
- 最终验收。

规则：

- 低于300/300时，不得进入下一轮；
- 先做通用根因分析和修复；
- 无法恢复则回滚修改；
- 不得恢复题目定向规则；
- 所有真实命令、结果路径和哈希必须留档。

## 5. 新100题设计

每轮100题：80道可回答，20道拒答或澄清。

所有题只基于官方500文档。无需100题覆盖全部500文档，但题目应来自完整语料池，并优先银行实际常用场景。

### 5.1 可回答题建议结构

- 单一制度事实、定义、职责：20；
- 阈值、期限、适用对象、例外、流程：12；
- 同文档多事实综合：10；
- 跨文档制度比较或证据组合：8；
- Excel单元格精确取数：12；
- 表格比较、差值、占比、同比、环比、合计：10；
- Word/PDF公式、变量和计算规则：4；
- 制度与统计报表联合判断：4。

数量可微调，但不得有明显能力缺项。

### 5.2 拒答题建议结构

- 资料库完全无依据；
- 缺少机构、期间、指标、口径或情境条件；
- 条件不足，不能得到唯一计算结果；
- 版本、适用范围或权威依据不足；
- 需要预测、因果、主观建议或外部实时数据。

拒答应说明缺少什么依据，不能只说“无法回答”。

### 5.3 难度与业务合理性

- 参考官方300道选择题，整体相当，可略微提高综合度；
- 简单30、中等35、困难35；
- 难度来自检索、表格、证据组合或计算步骤，不来自绕口、歧义和冷僻陷阱；
- 每题必须符合银行统计报送、合规、风险、监管查询等真实使用规律；
- 建议每轮至少40份不同来源文档，单文档原则上不超过5题。

## 6. “全新题目”定义

Round 1、2、3必须是三套独立题集。

禁止：复制历史题、同义改写、统一加前后缀、继承完整金标后改问法、仅改变数字格式或机构称呼、相同证据与结论换一种表达。

与以下集合去重：

- 官方300题；
- trust_challenge_100；
- hard_challenge_50；
- hard_challenge_70；
- 所有已生成轮次；
- 仓库中其他历史挑战题。

去重包括：规范化字符串、实体和关键词、embedding语义、来源证据位置、答案结论、推理结构。

同一来源文档可再次使用，但必须测试新的有效证据、条件组合或能力。

## 7. 金标定义和目录隔离

金标（Gold Standard）是标准判定依据，包含：

- 标准答案和可接受表达；
- 必需结论和禁止结论；
- 必需来源；
- 证据Aspect；
- 表格行列、sheet、cell、单位和期间；
- 计算操作数、公式、中间结果、精度和舍入；
- 拒答原因和期望拒答类型。

公开目录示例：

```text
data/evaluation/generalization_100/round_01/public/questions.jsonl
data/evaluation/generalization_100/round_01/lock.json
data/evaluation/generalization_100/round_01/public_audit_summary.json
```

私有目录放在主仓库外：

```text
..\ReguMate-Eval-Private\generalization_100\round_01\gold.jsonl
..\ReguMate-Eval-Private\generalization_100\round_01\detailed_audit.json
..\ReguMate-Eval-Private\generalization_100\round_01\scoring_config.json
```

公开题不得包含答案、证据原文、正确文件名、chunk、sheet、cell、计算过程、必需/禁止结论或标准拒答理由。

### 7.1 实际隔离方式

首选：

- 出题/审计在独立Codex会话或独立工作区中完成；
- 私有目录不位于优化Codex的允许工作区；
- 冻结后，通过NTFS权限、沙箱范围或临时移走私有目录，阻止优化阶段读取；
- scorer独立运行，只输出安全诊断包。

仅靠提示词“不要读取”不算强隔离。若环境无法做到权限隔离，报告必须明确降级为流程隔离。

## 8. 金标建议结构

```json
{
  "id": "R01-001",
  "question": "……",
  "answerable": true,
  "question_type": "table_calculation",
  "difficulty": "medium",
  "canonical_answer": "……",
  "acceptable_answers": [],
  "required_conclusions": [],
  "forbidden_conclusions": [],
  "required_sources": [],
  "required_evidence_aspects": [],
  "calculation": null,
  "expected_refusal_code": null,
  "refusal_rationale": null,
  "business_relevance": "……",
  "audit_status": "codex_verified"
}
```

表格证据应有文件SHA、标题、sheet、表名、行列、多级表头路径、cell、原值、单位、期间。

Word/PDF证据应有文件SHA、标题、页码或稳定位置、章节/条款、最小充分证据、发文机关、日期、文号、版本和公式。

## 9. GPT出题与独立审计

题目由GPT在独立出题阶段依据原始500份文档完成，仓库不提供或依赖题目生成器脚本。审计必须由独立阶段和不同数据流完成，重新读取原始500份文档，不直接信任GPT的出题结论。仓库中的评测管线仅负责公开投影、冻结、完整性校验、runner和scorer，不负责自动生成题目。

审计包括：

1. 条件完整、无歧义、符合银行使用规律；
2. 答案可由语料唯一推出；
3. canonical answer、required conclusions和证据无矛盾；
4. 数字、日期、机构、文号、规范强度、单位和期间正确；
5. 表格sheet、行列、cell和多级表头正确；
6. 公式符号、操作数、Decimal精度和舍入正确；
7. 跨文档每个来源都必要；
8. 版本、实施时间和适用对象明确；
9. 拒答题确实无充分依据或缺条件；
10. 无多个同样合理但金标不接受的答案；
11. 与历史题无实质重复；
12. 公开题无答案泄漏。

确定性内容必须用程序复核：Excel解析器、Decimal、必要时SymPy、文件/sheet/cell/条款存在性检查。高风险题使用第二条独立解析路径。

审计失败题废弃并重新生成，直至得到100道有效题。

## 10. 冻结、坏题和首跑

冻结前发现坏题：修复或替换，重跑全量审计，重新生成哈希。

首跑后发现坏题：

- 保留原题、金标、结果、评分和哈希；
- 标记 `invalid_case` 并注明原因；
- 生成、审计、冻结和首跑替补题；
- 最终分母恢复为100道有效题；
- 不得修改坏题后仍称原结果为首次盲测。

在线runner只读公开题并调用 `/api/qa/ask`。离线scorer读取私有金标、原始API输出和锁文件。

## 11. 评分指标

新100题门槛：

| 指标 | 门槛 |
|---|---:|
| 总通过率 | >= 90% |
| 制度事实类准确率 | >= 85% |
| 表格取数类准确率 | >= 80% |
| 必需来源命中率 | >= 90% |
| 必需证据Aspect完整率 | >= 90% |
| 拒答/澄清准确率 | >= 80% |
| 关键数字、日期、机构、文号错误率 | <= 5% |
| 官方300题 | 300/300 |
| P95延迟 | 仅记录 |

单题判分综合：语义正确、结论完整、无禁止结论、关键实体正确、引用真实且支持答案、来源与证据Aspect满足、计算可验证、拒答边界正确。

不得忽略数值、单位、期间、主体、规范强度和跨文档缺失。

评分器版本和哈希在冻结时写入lock。冻结后实质修改评分器，则该轮作废，使用新版本重新冻结和首跑。

## 12. 安全诊断包

优化阶段只能收到：

- case ID和公开问题；
- 系统原始回答；
- 是否通过；
- 失败层级和类别；
- 黄金证据是否进入召回/rerank/最终上下文的布尔值；
- 预期与实际来源数量；
- 预期与命中Aspect数量；
- 单位、期间、主体、符号、计算、规范强度错误标签；
- 延迟、超时、环境错误。

不得包含标准答案、标准数值、完整证据原文、正确文件名、cell、chunk或禁止结论。

失败类别：corpus_missing、parse_loss、chunking_loss、retrieval_recall、metadata_filter、rerank_drop、context_truncation、table_location、table_header、formula_parse、calculation、unit_period、cross_document_coverage、version_scope、answer_generation、citation_grounding、refusal_boundary、evaluator_or_gold_issue、timeout_or_environment。

## 13. 三轮流程

### Phase 1：基线与去硬编码

- 记录环境和官方300题基线；
- 全仓审计并删除定向硬编码；
- 建立反硬编码和质量门禁；
- 通过通用能力恢复官方300/300；
- 更新STATE并提交。

### Phase 2：评测基础设施

- 建立生成、审计、冻结、runner、scorer、安全诊断；
- 建立主仓库外私有目录和隔离检查；
- 使用少量合成题验证数据流；
- 不进行正式Round 1；
- 官方300/300后提交。

### Round 1

- 生成、审计和冻结第一批100题；
- 保存首次盲测原始结果；
- 根据安全诊断做通用修复；
- 失败题只作为回归，不再称盲测；
- 官方300/300后提交。

### Round 2

- 生成独立第二批100题；
- 首跑、归因和通用修复；
- 回归官方300、Round 1和历史挑战；
- 官方300/300后提交。

### Round 3

- 生成独立第三批100题；
- 首次盲测作为最终泛化验收；
- 同时运行官方300、Round 1、Round 2、工程测试、反硬编码和环境验证。

若Round 3首跑未达标，可修复和回归，但不能称最终泛化已验证。需要新的Round 4才能获得新的独立验收；本协议默认不自动启动Round 4。

## 14. 工程和Git规则

建议分支：`codex/generalization-no-hardcode-3round`。

建议提交：基线、去硬编码、门禁、评测基础设施、每轮冻结、每轮通用修复、最终报告分别提交。

任何有效提交前：

- 官方300/300；
- 反硬编码审计通过；
- 冻结哈希检查通过；
- 后端测试和适用的前端验证通过；
- 无密钥泄漏；
- STATE和交接文件更新。

允许删除临时缓存、未冻结草稿和可再生成中间文件。不得删除已冻结题集、首跑结果、报告、锁、哈希和有效Git历史。

## 15. `.env` 保护

- 保留DeepSeek环境变量名称和值；
- 不在输出中打印值；
- 仅保存不可逆哈希用于前后比对；
- 不擅自改变Git跟踪状态；
- 日志、报告、测试夹具和提交信息不得泄漏密钥。

## 16. 最终结论

只能输出：

- `PASS`：官方300/300；Round 3首次盲测全部达标；反硬编码和工程门禁通过。
- `OFFICIAL_PASS_GENERALIZATION_NOT_VERIFIED`：官方300/300，但Round 3首跑未全部达标，或只在同一题集修复后达标。
- `FAIL`：官方300未保持300/300、仍有评测定向硬编码或关键工程门禁失败。

三轮属于Codex自生成、自审计、流程隔离的内部盲测，不得描述为第三方或银行专家评审。

# Vibe Coding 实战教程

这篇文档教你如何把 AI 当成受控的工程协作者。核心原则：你先定义目标、边界、验收标准；AI 负责读少量必要上下文、给出改法、在你明确要求后再执行。

## 1. 最终要实现什么效果

你应该能写出这样的任务：

```text
请先阅读 AGENTS.md 和 docs/开发文档/API接口设计.md。
目标：实现 POST /reports/upload 的最小版本。
允许修改：backend/app/api、backend/app/schemas、backend/app/services、backend/main.py、backend/app/tests。
禁止修改：前端、RAG、Agent。
验收：pytest 通过；Swagger 能上传 CSV；不支持文件类型返回 400。
请先说明怎么改，我确认后再执行。
```

## 2. 使用 AI 前先准备什么

每次准备 6 个信息：

| 信息 | 示例 |
| --- | --- |
| 目标 | 新增报表上传 API |
| 必读文档 | `AGENTS.md`、`API接口设计.md` |
| 允许修改 | `backend/app/api` |
| 禁止修改 | 不改前端、不引入数据库 |
| 输入输出 | 上传 CSV，返回 report_id |
| 验收标准 | pytest 通过，Swagger 可测 |

## 3. 默认流程

1. 让 AI 读最少上下文。
2. 让 AI 说明修改方案。
3. 你确认后，再说“直接修改”。
4. AI 小步修改。
5. AI 运行测试或说明无法运行。
6. AI 总结改了什么、怎么验证。
7. 你人工 review。

## 4. 新增功能怎么问

模板：

```text
请先阅读 AGENTS.md 和 docs/开发文档/<相关文档>.md。

我要新增功能：

目标：
输入：
输出：
允许修改：
禁止修改：
验收标准：
测试要求：

请先告诉我开发步骤和文件修改建议，不要直接改代码。
```

确认后：

```text
直接按刚才方案修改代码。
```

## 5. 修 bug 怎么问

模板：

```text
请先阅读 AGENTS.md 和相关模块代码。

问题：
复现步骤：
期望结果：
实际结果：
允许修改：
验收标准：

请先定位原因，给出最小修复方案。我确认后再改。
```

确认后：

```text
直接执行最小修复，并补充测试。
```

## 6. 写测试怎么问

模板：

```text
请先阅读 AGENTS.md 和 docs/开发文档/测试与验收.md。

目标模块：
需要覆盖：
已有样例：
禁止修改业务逻辑：
验收命令：

请先说明测试用例设计，再等我确认。
```

## 7. 写文档怎么问

模板：

```text
请把 docs/开发文档/<文档名>.md 重写成新手教程。
要求：
1. 不要写文档受众、阅读时机、内容边界这类规划章节。
2. 要写最终效果、涉及文件、一步步开发、代码示例、测试、常见错误、完成标准。
3. 面向开发者，不是面向 Agent。
```

## 8. 让 AI 小步改

可以加这些限制：

```text
本次最多改 5 个文件。
不要重构无关模块。
不要新增依赖。
不要修改已有测试之外的行为。
每完成一个模块先说明。
```

## 9. 如何防止 AI 编造

提示词：

```text
不得编造不存在的接口、字段、路径、依赖。
如果文档或代码中找不到，请说明缺失，不要猜。
字段必须来自当前 schema 或本次明确要求。
制度依据必须来自 RAG 检索结果。
```

## 10. 如何检查 AI 的结果

检查清单：

- 文件路径是否正确。
- 改动是否超出范围。
- 是否有测试。
- 是否能运行。
- 是否有错误处理。
- 是否更新相关文档。
- 是否需要更新 `AGENTS.md`。
- 是否泄露真实数据。

## 11. AI 写错后怎么办

不要马上全仓库回滚。先做三步：

```powershell
git status
git diff
```

然后告诉 AI：

```text
刚才实现有问题。请只查看你本次修改的文件，说明问题原因，给出最小修复。不要回滚其他文件。
```

如果确实要撤销，明确指定文件。

```text

```

## 13. 完成标准

- 每次 AI 任务有目标、边界和验收。
- AI 默认先讲方案，不直接改代码。
- 明确要求后才执行修改。
- 修改后必须说明改了什么、为什么改、怎么验证。
- 人工 review 后再进入提交。

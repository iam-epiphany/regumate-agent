## 1. 项目定位

FilingSentry Agent 是一个面向银行监管统计报送场景的智能体项目。它不是普通制度问答系统，也不是单纯的报表校验脚本，而是把可信 RAG、规则引擎、工具调用、结构化输出、人工复核和历史经验沉淀组合起来，形成一条可以演示、可以学习、可以继续扩展的完整工程链路。

项目核心问题是：

> 如何用可信 RAG、规则引擎和 Agent 工作流，帮助监管报送人员完成制度问答、报表自检、异常排查、根因分析、修复建议、人工复核和经验沉淀？

本项目面向的典型场景：

- 填报人员不知道某个字段应该按什么口径填。
- 填报人员不确定某个指标是否应该纳入统计。
- 报表字段缺失或格式错误。
- 合计项和明细项不一致。
- 表内或表间勾稽关系不通过。
- 本期数据较上期出现异常波动。
- 数据来源字段可能映射错误。
- 系统发现异常后，人工不知道从哪里开始排查。
- 处理经验没有沉淀，下次类似问题仍然重复出现。

项目第一阶段强调“新手能做出来”。因此不把复杂知识图谱、多 Agent、LangGraph 作为主线，而是先用 FastAPI、OpenAI Agents SDK、JSON、JSON/YAML 规则、Markdown 报告和 React 做出完整闭环。

## 2. 最终产品目标

最终要做一个可运行的网页系统。

用户打开系统后，应该可以完成以下演示链路：

1. 在可信问答页面输入监管制度或字段口径问题。
2. 系统基于制度文档、填报说明和字段定义返回带引用的答案。
3. 用户上传或选择一份样例监管统计报表。
4. 系统自动执行数据质量规则检查。
5. 前端展示异常列表、涉及字段、命中规则和建议处理状态。
6. 用户点击某个异常，触发 Agent 智能排查。
7. Agent 调用报表读取、规则校验、制度检索、字段定义检索、历史案例检索和证据链工具。
8. 系统输出可能根因、支持证据、缺失证据和下一步复核建议。
9. 用户填写人工复核结论和最终处理方式。
10. 系统保存历史异常案例。
11. 系统生成 Markdown 审查报告。
12. 下次遇到类似异常时，Agent 能提示历史处理经验。

第一版目标：

- 能问：制度和字段口径问题可基于 RAG 回答。
- 能查：样例报表可被读取和规则检查。
- 能排：异常可被 Agent 按工具流程排查。
- 能解释：每个结论都有证据和来源。
- 能复核：人工可确认或修正 Agent 建议。
- 能沉淀：复核结果可保存为历史案例。
- 能展示：React 页面可以完整演示。
- 能学习：两名新手能通过项目掌握 Agent 工程基本方法。

## 3. 核心功能

### 3.1 可信问答

用户可以针对监管制度、统计报表、字段口径和填报说明提问。

示例问题：

- “普惠小微贷款余额字段应该如何填报？”
- “这个字段是否包含展期贷款？”
- “表 A 的合计项和表 B 的某个字段有什么关系？”
- “如果某字段为空，是否影响监管报送？”

回答必须基于检索结果，不能让大模型凭空回答。

回答结构：

- 直接答案。
- 引用制度或填报说明。
- 来源片段。
- 相关字段。
- 置信度。
- 常见填报错误。
- 是否建议人工复核。

无依据时必须明确说明：

> 当前知识库没有足够依据确认该问题，建议人工复核或补充制度文档。

### 3.2 报表自检

用户可以上传 Excel/CSV，第一版也可以直接选择系统内置样例报表。

系统自动检查：

- 必填字段是否为空。
- 金额是否为负。
- 日期格式是否正确。
- 合计项是否等于明细项。
- 表内勾稽关系是否满足。
- 表间勾稽关系是否满足。
- 本期数据较上期是否异常波动。
- 字段取值是否符合填报口径。
- 是否存在需要人工复核的异常。

第一版建议使用 JSON/CSV 样例报表和自定义规则，不依赖真实银行数据。

### 3.3 智能排查

发现异常后，Agent 不只是提示“这个字段不通过”，而是调用工具完成排查。

标准排查流程：

1. 读取报表字段。
2. 执行规则校验。
3. 查询字段定义。
4. 检索监管制度。
5. 检索填报说明。
6. 检索历史相似异常案例。
7. 汇总异常证据。
8. 生成可能根因。
9. 给出下一步复核建议。

该流程必须体现 Tool Calling / Function Calling，而不是纯规则脚本。

### 3.4 根因分析

对每个异常，系统输出结构化根因分析。

示例异常：

> 贷款余额汇总值与明细合计不一致。

可能根因：

- 明细记录遗漏。
- 汇总字段口径错误。
- 字段映射错误。
- 上游数据源导出不完整。
- 人工填报错误。
- 新旧监管口径混用。

根因分析结构：

- 异常名称。
- 涉及字段。
- 命中规则。
- 支持证据。
- 可能根因。
- 缺失证据。
- 下一步检查建议。
- 是否需要人工复核。

### 3.5 人工复核

系统不替代人工最终判断。对于中高关注度异常或证据不足的异常，必须进入人工复核。

人工复核内容：

- 复核结论。
- 最终处理方式。
- 原因说明。
- 是否采纳 Agent 建议。
- 是否生成历史案例。
- 是否生成 playbook。

### 3.6 闭环沉淀

人工复核后，系统保存本次异常处理结果。

沉淀内容包括：

- 异常类型。
- 涉及字段。
- 命中规则。
- 制度依据。
- Agent 给出的根因。
- 人工复核结论。
- 最终处理方式。
- 下次遇到类似异常的处理建议。
- 是否生成 playbook。

下次遇到类似异常时，Agent 可以提示：

> 历史上出现过类似异常，当时原因是字段映射错误，建议优先检查字段映射表。

## 4. 版本路线

### V0：可信 RAG 问答最小闭环

为什么先做：

监管报送 Agent 的基础是可信依据。如果制度、字段和填报说明都不能可靠引用，后续自检和排查就缺少可信基础。

做什么：

- 准备监管制度、填报说明和字段定义样例。
- 用 JSON 保存文档片段。
- 实现关键词检索或轻量向量检索。
- 接入 OpenAI Agents SDK。
- 编写 `search_regulation_tool`。
- 编写 `get_field_definition_tool`。
- 编写 `answer_with_citations_tool` 或等价结构化输出流程。
- 前端实现可信问答页面。
- 展示 Agent Trace。

产出：

- 一组制度与字段样例数据。
- 一个可运行 FastAPI 问答接口。
- 一个 OpenAI Agents SDK 单 Agent。
- 一个可信问答页面。
- 一组问答测试样例。

验收：

- 输入字段口径问题，系统能返回带引用的答案。
- 回答中包含直接答案、来源片段、相关字段、置信度和复核建议。
- 知识库没有依据时，系统不能编造答案。
- Agent Trace 中能看到检索工具调用。

### V1：报表自检闭环

为什么做：

只有问答还不够。监管报送项目必须能检查报表数据质量，才能区别于普通 RAG 问答系统。

做什么：

- 准备样例监管报表 JSON/CSV。
- 准备字段定义表。
- 准备规则配置文件。
- 实现 `report_reader`。
- 实现 `rule_engine`。
- 编写 `read_report_tool`。
- 编写 `run_validation_rules_tool`。
- 编写 `calculate_issue_level_tool`。
- 前端实现报表上传和自检结果页。

规则类型：

- 必填字段检查。
- 非负检查。
- 日期格式检查。
- 合计项检查。
- 表内勾稽检查。
- 表间勾稽检查。
- 跨期波动检查。
- 字段枚举值检查。

产出：

- 样例监管报表。
- 规则库 JSON/YAML。
- 自检 API。
- 异常列表页面。
- 自检结果 JSON。

验收：

- 系统能稳定识别至少 6 类异常。
- 每个异常都包含异常名称、涉及字段、命中规则、证据值和建议状态。
- 异常等级来自工具计算，不由 LLM 直接生成。

### V2：智能排查与根因分析

为什么做：

只列出异常还不够。项目亮点是 Agent 能主动调用工具，帮助用户查原因、找依据、形成下一步检查建议。

做什么：

- 编写 `get_issue_detail_tool`。
- 编写 `search_reporting_guidance_tool`。
- 编写 `search_historical_cases_tool`。
- 编写 `build_evidence_chain_tool`。
- 编写 `root_cause_analysis_tool`。
- 使用 OpenAI Agents SDK 组织工具调用。
- 增加结构化输出 schema。
- 增加 Guardrails 校验。
- 前端实现异常详情和智能排查页。

产出：

- 异常排查 Agent。
- 根因分析结构化结果。
- Agent 工具调用轨迹。
- 证据链卡片。
- 根因分析 Markdown 片段。

验收：

- 对单个异常，Agent 至少调用 4 类工具。
- 输出包含可能根因、支持证据、缺失证据和下一步建议。
- 所有字段、规则、来源片段都可追溯到工具结果。
- Guardrails 能发现缺少来源或字段不存在的问题。

### V3：人工复核与闭环沉淀

为什么做：

监管报送场景不能让 Agent 直接替代人工判断。更合理的方式是让 Agent 辅助排查，人工复核，系统沉淀处理经验。

做什么：

- 实现人工复核队列。
- 实现复核记录保存。
- 实现历史案例入库。
- 实现相似案例检索。
- 实现 Markdown 报告生成。
- 前端实现复核页面和报告预览页面。

产出：

- 待复核异常列表。
- 复核记录 JSON。
- 历史案例库。
- Markdown 审查报告。
- 报告导出入口。

验收：

- 用户能提交复核结论。
- 复核结果能保存为历史案例。
- 下一次排查相似异常时能检索到历史案例。
- 系统能生成完整 Markdown 报告。

### V4：多 Agent 与复杂编排增强

为什么后做：

多 Agent 和 LangGraph 很适合展示高级架构，但新手一开始使用容易把项目做成框架学习，而不是业务闭环。应在 V0-V3 稳定后再增强。

做什么：

- 将单 Agent 能力拆分为可信问答 Agent、自检 Agent、排查 Agent、报告 Agent、复核沉淀 Agent。
- 保持工具层复用，不重写核心工具。
- 可选引入 LangGraph 管理状态流、分支流程和失败重试。
- 前端展示多 Agent 协作过程。

产出：

- 多 Agent 架构说明。
- LangGraph 可选流程图。
- 多 Agent Trace 展示。
- 升级后的演示链路。

验收：

- V4 不破坏 V0-V3 功能。
- 多 Agent 只是增强组织方式，规则、证据和等级仍由工具产生。
- LangGraph 作为后续增强，不成为第一阶段交付前置条件。

## 5. 系统架构

后端使用 **FastAPI**。

Agent 主线使用 **OpenAI Agents SDK**。

第一阶段数据使用 **JSON**。

规则使用 **JSON/YAML**。

报告使用 **Markdown 报告**。

前端使用 **React + Vite**。

后续可升级到 SQLite、向量数据库、LangGraph 和多 Agent。

架构原则：

- LLM 负责理解任务、选择工具、组织解释和生成报告。
- 工具负责读取事实、执行规则、计算异常等级和生成证据。
- 报表数据对错由规则引擎检查。
- 异常等级由工具计算。
- 制度依据来自 RAG 检索结果。
- Agent 输出必须经过 Guardrails 校验。
- 无 API Key 时可保留模板 fallback，但正式主线是 OpenAI Agents SDK 工具调用。

### 5.1 Agent 架构判断

| 架构 | 是否作为主线 | 原因 |
| --- | --- | --- |
| 纯规则脚本 | 不作为主线 | 能检查数据，但体现不出 Agent 工具调用 |
| 普通 RAG 问答 | 不作为主线 | 能回答制度问题，但无法完成自检和排查闭环 |
| 纯 ReAct | 不作为主线 | 新手不易控制，容易出现重复调用或漏调用 |
| OpenAI Agents SDK Tool Calling | V0-V3 主线 | 新手友好，能体现工具调用、Trace 和结构化输出 |
| Plan-and-Execute-lite | V2 可加入 | 先生成排查计划，再按计划调用工具，更利于展示 |
| 多 Agent | V4 增强 | 等单 Agent 稳定后再拆分职责 |
| LangGraph | V4 可选 | 适合复杂状态流，但不作为第一阶段主线 |

### 5.2 后端模块

| 模块 | 作用 | 新手理解 |
| --- | --- | --- |
| `doc_service` | 管理制度文档和填报说明片段 | 知识库入口 |
| `field_service` | 管理字段定义和填报口径 | 字段字典 |
| `report_service` | 读取样例报表和上传文件 | 报表数据入口 |
| `rule_engine` | 执行配置化规则 | 判断哪里不符合要求 |
| `case_service` | 保存和检索历史异常案例 | 经验库 |
| `review_service` | 保存人工复核记录 | 人工闭环 |
| `llm_service` | 封装模型调用 | 避免 API 调用散落 |
| `tools/` | 封装 Agent 可调用工具 | Agent 能力清单 |
| `filing_sentry_agent` | 组织完整 Agent 流程 | 主控流程 |
| `guardrails` | 校验输出是否越界 | 防止编造依据 |
| `trace_service` | 记录计划和工具调用 | 前端展示 Agent Trace |
| `markdown_report_service` | 生成 Markdown 报告 | 输出审查报告 |
| `api` | 提供前端接口 | 网页调用后端 |

## 6. 数据方案

第一版不用真实银行数据，只使用模拟监管报表和公开可描述的制度样例片段。

### 6.1 制度文档与填报说明

文件：`regulatory_docs.json`

用途：

- 保存制度片段。
- 保存填报说明。
- 保存来源标题。
- 保存章节编号。
- 保存适用字段。

示例结构：

```json
{
  "doc_id": "DOC-001",
  "title": "监管统计填报说明样例",
  "section": "2.1 普惠小微贷款余额",
  "content": "本字段用于填报符合口径要求的普惠小微贷款期末余额。",
  "related_fields": ["inclusive_micro_loan_balance"],
  "source_type": "reporting_guidance"
}
```

### 6.2 字段定义表

文件：`field_definitions.json`

用途：

- 定义字段中文名。
- 定义字段英文名。
- 定义数据类型。
- 定义是否必填。
- 定义填报口径。
- 定义常见错误。

示例结构：

```json
{
  "field_code": "inclusive_micro_loan_balance",
  "field_name": "普惠小微贷款余额",
  "table_code": "REP-A",
  "data_type": "decimal",
  "required": true,
  "definition": "符合普惠小微口径的贷款期末余额。",
  "common_errors": ["未剔除不符合口径的金额", "与明细项汇总不一致"]
}
```

### 6.3 样例监管报表

文件：`sample_reports.json`

用途：

- 保存本期报表。
- 保存上期报表。
- 保存明细项。
- 保存合计项。
- 支持跨期波动检查。

示例结构：

```json
{
  "report_id": "RPT-2026-001",
  "period": "2026Q2",
  "table_code": "REP-A",
  "rows": [
    {
      "field_code": "inclusive_micro_loan_balance",
      "current_value": 1250000.00,
      "previous_value": 860000.00,
      "unit": "CNY"
    }
  ]
}
```

### 6.4 校验规则库

文件：`validation_rules.json` 或 `validation_rules.yaml`

规则类型：

- `required`
- `non_negative`
- `date_format`
- `sum_equals_details`
- `intra_table_relation`
- `inter_table_relation`
- `period_over_period_change`
- `enum_value`

示例结构：

```json
{
  "rule_id": "RULE-001",
  "rule_name": "普惠小微贷款余额不能为空",
  "rule_type": "required",
  "target_table": "REP-A",
  "target_fields": ["inclusive_micro_loan_balance"],
  "severity": "medium",
  "review_required": true,
  "message": "普惠小微贷款余额为必填字段，不能为空。"
}
```

### 6.5 历史异常案例库

文件：`historical_cases.json`

用途：

- 保存异常类型。
- 保存涉及字段。
- 保存制度依据。
- 保存 Agent 根因。
- 保存人工结论。
- 保存最终处理方式。
- 保存下次建议。

### 6.6 人工复核记录

文件：`review_records.json`

用途：

- 保存待复核、已确认、已修复、暂缓处理等状态。
- 保存人工备注。
- 保存是否生成历史案例。
- 支持闭环沉淀。

## 7. Agent 设计

### 7.1 LLM 定位

LLM 负责：

- 理解用户问题。
- 判断应该调用哪些工具。
- 组织制度问答。
- 生成自然语言解释。
- 生成根因分析草案。
- 生成 Markdown 报告。
- 支持用户追问。

LLM 不负责：

- 不直接判断报表数据对错。
- 不直接生成异常等级。
- 不编造制度依据。
- 不编造字段。
- 不编造规则。
- 不编造报表数据。
- 不替代人工复核结论。

### 7.2 工具定位

工具负责：

- 读取报表。
- 执行规则检查。
- 检索制度文档。
- 检索字段口径。
- 检索历史案例。
- 生成证据链。
- 计算异常等级。
- 保存复核结果。

### 7.3 V0 单 Agent

Agent 名称：`FilingSentryAgent`

职责：

- 接收用户问题。
- 调用制度检索工具。
- 调用字段定义工具。
- 组织可信回答。
- 返回引用来源和复核建议。

### 7.4 V2 Plan-and-Execute-lite

排查异常时，可以让 Agent 先生成结构化排查计划，再按计划调用工具。

计划示例：

```json
{
  "goal": "排查普惠小微贷款余额合计不一致异常",
  "steps": [
    "读取异常详情",
    "查询涉及字段定义",
    "检索填报说明",
    "查询命中规则",
    "检索历史相似案例",
    "构建证据链",
    "生成根因分析"
  ]
}
```

这样既能体现 Agent 的计划能力，又不会像完整复杂编排框架那样增加过高难度。

### 7.5 V4 多 Agent

V4 才拆分多 Agent：

| Agent | 职责 |
| --- | --- |
| `RegulationQAAgent` | 制度问答和字段口径解释 |
| `ReportCheckAgent` | 报表自检流程组织 |
| `InvestigationAgent` | 异常排查和根因分析 |
| `ReviewAgent` | 人工复核和闭环记录 |
| `ReportWriterAgent` | Markdown 报告生成 |

V4 之前不要过早拆分，避免新手同时维护过多抽象。

## 17. 风险控制

| 风险 | 表现 | 解决办法 |
| --- | --- | --- |
| 范围过大 | 同时做问答、自检、复杂编排、生产平台 | 按 V0-V4 分阶段推进 |
| Agent 太虚 | 只让 LLM 写解释 | V0 起展示工具调用和 Trace |
| RAG 不可信 | 回答没有来源 | 强制返回引用片段和置信度 |
| LLM 编造 | 出现不存在字段或依据 | Guardrails 校验字段、规则和来源 |
| 规则太死 | 所有逻辑写在代码里 | 用 JSON/YAML 配置规则 |
| 前后端脱节 | 页面等接口，接口等页面 | 先固定 API 契约 |
| 新手学不动 | 一开始引入过多框架 | 先 FastAPI + OpenAI Agents SDK + JSON + React |
| 演示不稳定 | API Key 或网络问题影响展示 | 保留工具层 fallback 和样例结果 |
| 数据不真实 | 只有随手编的样例 | 明确模拟数据目的，补充规则说明 |
| 报告不可读 | 输出散乱 | 使用固定 Markdown 模板 |
| 人工闭环缺失 | 系统只提示异常 | V3 必须支持复核保存和案例沉淀 |

项目推进口诀：

> 完整闭环 > 功能数量  
> 可信证据 > 炫酷概念  
> 能跑起来 > 架构复杂  
> OpenAI Agents SDK 主线 > LangGraph 后续增强  
> 工具负责事实 > LLM 负责解释  
> 人工复核闭环 > 自动替代判断

## 19. 默认决策

- 项目中文名固定为“FilingSentry Agent：面向银行监管报送的可信自检与智能排查智能体”。
- 推荐正式题目固定为“基于可信 RAG 与主动排查工作流的银行监管报送智能自检与根因分析平台”。
- 第一阶段技术栈固定为 FastAPI、OpenAI Agents SDK、JSON、JSON/YAML、Markdown 报告、React + Vite。
- 第一阶段不接真实银行数据。
- 第一阶段不做生产级权限系统。
- 第一阶段不把 LangGraph 作为主线。
- 第一阶段不做复杂多 Agent。
- V0 先做可信问答。
- V1 做报表自检。
- V2 做智能排查与根因分析。
- V3 做人工复核与闭环沉淀。
- V4 再考虑多 Agent 和 LangGraph。
- LLM 负责理解、调度、解释和报告。
- 工具负责事实、规则、等级和证据。
- 无依据时系统必须提示无法确认。
- 所有核心输出都要能被人工复核。

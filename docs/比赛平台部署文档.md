# ReguMate Agent 决赛部署文档

版本日期：2026-10-22。目标环境：Linux x86_64 / linux/amd64。
作品：面向银行业监管制度与统计报表的可信 RAG 问答。

## 1. 提交材料与运行方式

向比赛平台分别上传本部署文档 PDF 和完整项目 ZIP。不要仅上传源码目录或镜像 tar。ZIP 支持 ZIP64，解压工具须支持超过 4 GiB 的文件。

本包提供前后端源码、依赖声明及锁文件、启动脚本、应用镜像、Qdrant 镜像、完整本地模型、原始资料、知识库快照和根目录 `.env`。镜像已含前端构建结果、Python 依赖、LibreOffice、antiword 和中文字体；部署机器无需安装 Python、Node.js、Office 或访问依赖仓库。

应用镜像：`regumate/app:submission-20261022-amd64`；向量库镜像：`qdrant/qdrant:v1.18.0`。两者均为 `linux/amd64`。镜像归档位于 `images/regumate-linux-amd64.tar`。实际文件大小、模型和知识库数量见 `OFFLINE_MANIFEST.json`。

## 2. 平台资源与依赖

- 必需：Linux amd64、运行中的 Docker Engine、支持 Compose V2 语法的 Docker Compose 插件、可读写的项目目录与 Docker 数据目录。
- CPU 模式为默认：建议 8 vCPU、32 GiB 内存；大模型为外部 API，CPU 只运行本地检索及重排。此配置是建议值，不是最低要求或吞吐量承诺。
- GPU 模式可选：建议 NVIDIA GPU 显存 16 GiB 起步，另需兼容镜像内 CUDA/PyTorch 的宿主机 NVIDIA 驱动和 NVIDIA Container Toolkit。GPU 未配置时直接使用 CPU 启动命令。
- 建议至少 150 GiB 可用 SSD，覆盖压缩包、解压文件、镜像导入、模型、数据库运行卷及后续上传资料；这也是容量预留建议。
- 主机只需向部署入口开放 `SERVICE_PORT`（默认 TCP 8000）。Qdrant 6333/6334 仅在容器网络内使用，不映射至主机。
- 完整问答需要应用容器能够通过 HTTPS 访问 `.env` 中的国产大模型 API。部署过程中不下载模型和依赖，但答案生成仍需 API 网络与可用额度。若平台无外网，应提供平台内可达的兼容模型接口，修改供应商、服务地址、模型名称与 Key 后重启并验收。

## 3. 配置说明

根目录 `.env` 已含项目所有者授权随包提供的真实 API Key，仅供本作品部署使用；本文、源码、Dockerfile 和镜像均不保存该 Key。不得将整个提交包或 `.env` 发布到公开仓库。承办方可以替换为自己的凭据。

- `MODEL_PROVIDER`：国产模型供应商，当前 DeepSeek（深度求索）。
- `MODEL_API_KEY`：模型凭据，实际值仅在 `.env`。
- `MODEL_BASE_URL`：当前 `https://api.deepseek.com`，不带 `/chat/completions` 后缀。
- `MODEL_NAME`：当前 `deepseek-v4-flash`。规划、生成和语义核验共用这套配置。
- `EMBEDDING_API_KEY`：留空；本地 BGE 模型不调用独立 Embedding API。
- `SERVICE_PORT`：默认 8000，同时控制容器监听、主机映射和健康检查，允许修改为未占用端口。
- `REGUMATE_BIND_ADDRESS`：提交包默认 `0.0.0.0`，供平台转发访问；仅在本机演示时可改为 `127.0.0.1`。
- `MODEL_DEVICE`：默认 `cpu`；GPU 启动配置覆盖为 `cuda`。
- `QA_REQUEST_TOTAL_BUDGET_SECONDS` / `QA_COMPLEX_REQUEST_TOTAL_BUDGET_SECONDS`：默认 300 / 600 秒，为 CPU 检索与多方面问题预留处理时间；CPU 模式的复杂问题可能需要数分钟。
- `REGUMATE_APP_IMAGE`：固定为本包应用镜像标签；与归档和清单保持一致。
- `QDRANT_COLLECTION`：默认 `regumate_chunks`，与随包快照对应，部署时保持不变。

本地检索权重路径由 Compose 设置为 `/app/data/models/bge-m3` 和 `/app/data/models/bge-reranker-v2-m3`。模型合计约 6.41 GiB，不需要下载生成式大模型权重。程序的数据路径均使用环境变量、项目相对路径或容器路径，不依赖开发电脑盘符。Compose 自动读取根目录 `.env`；宿主机同名环境变量会优先于文件，请避免沿用其他项目的端口、模型或镜像设置。

## 4. Linux 启动与访问

从压缩包解压后的项目根目录执行 CPU 默认启动：

```sh
sh scripts/offline/start.sh
```

GPU 主机改用：

```sh
sh scripts/offline/start.sh --gpu
```

脚本先执行 `docker load` 导入随包镜像，再执行 Compose，指定 `--no-build --pull never`，不拉取镜像、不安装依赖。脚本不需要执行位权限，文件使用 LF 行尾。Windows 本地复核可用 `powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\offline\start.ps1`，GPU 加 `-Gpu`。

等价 CPU 手动命令：

```sh
docker load -i images/regumate-linux-amd64.tar
docker compose -f docker-compose.offline.yml up -d --no-build --pull never
docker compose -f docker-compose.offline.yml ps
```

应用入口为 `python -m uvicorn backend.main:app --host 0.0.0.0 --port ${SERVICE_PORT:-8000} --workers 1`。网页路径 `/`，知识库 `/documents`，问答 `/qa`，操作记录 `/audit`，API 文档 `/docs`。前后端由同一端口提供，无需额外前端服务。平台访问地址使用承办方分配的域名或主机地址，路径建议使用域名根路径 `/`；静态资源与接口使用 `/assets/` 和 `/api/`，不要只转发网页 HTML。

如接入反向代理，请将网页、静态文件、`/api/` 全部转发到该端口；问答使用 SSE，代理应允许持续连接并关闭响应缓冲，复杂问答建议超时预留 660 秒。不要将 `0.0.0.0` 当作浏览器访问地址。

## 5. 知识库初始化与持久化

`db-init` 先把 `data/offline_seed/app.db` 恢复到新的 SQLite 命名卷，Qdrant 从 `data/offline_seed/regumate.snapshot` 恢复向量集合，随后应用启动并加载本地模型。种子提供 500 份已索引文档和 47,648 个文本块/向量点，保留引用所需原文件，不带源机器的问答会话和操作历史。

数据库使用 Docker 命名卷以避免共享目录的 SQLite 锁问题；模型只读挂载；新上传文件写入 `data/evaluation/final_runtime/documents/originals/`。首次恢复与模型加载需要等待，时长取决于机器资源。`db-init` 和 `qdrant-init` 显示 `Exited (0)` 是正常完成状态；后者在恢复后触发待处理的向量库优化，不修改向量和原文内容。

再次启动保留现有非空数据库与运行卷，不强制覆盖已存在的知识库。停止并保留数据：`docker compose -f docker-compose.offline.yml down`。不要附加 `-v`，该参数会删除命名卷。修改 `.env` 后执行相同启动命令应用新配置。迁移时保留整个解压目录并备份命名卷；种子仅反映本包交付时状态，不含部署后的新增数据。

## 6. 提交前及平台部署后验收

先在全新命名卷中启动；本包的实际复核结果见 `ACCEPTANCE_REPORT.md` 和 `acceptance/`。平台部署后还必须用平台地址再次完成以下检查：

1. 页面访问：打开 `/`、`/documents`、`/qa`、`/audit`，没有白屏、404、502、504 或长期启动提示。
2. 静态资源：图片、CSS、JavaScript 和字体完整加载，页面布局、按钮、跳转正常。
3. 服务与模型：`curl -fsS http://127.0.0.1:8000/api/health`、`curl -fsS http://127.0.0.1:8000/api/health/ready` 均正常；健康检查不能替代真实模型调用。
4. 完整业务：在知识库查看已有资料，再在可信问答中输入一条有原文支持的问题，例如“第三档商业银行的核心一级资本充足率最低要求是多少？”，确认返回有效答案及可打开的引用。这是功能检查示例，不是预置答案或题库命中规则。
5. 凭据和结果：核对 API 实际返回、生成状态及原文依据；不出现 Key 缺失、连接失败、超时或乱码。导出或查看操作记录验证相关交互。

可执行 `python scripts/offline/verify.py --base-url http://127.0.0.1:8000` 自动检查页面资源、健康、资料列表和一条无选项真实问答；此命令会消耗少量大模型额度并在测试部署中产生问答记录。平台端口改动后同步修改 URL。

## 7. 排障及平台操作注意事项

查看状态与日志：`docker compose -f docker-compose.offline.yml ps -a`、`docker compose -f docker-compose.offline.yml logs --tail 100 app qdrant db-init qdrant-init`。向外提供日志前确认不含凭据。

- 端口被占用或平台访问不到：修改 `SERVICE_PORT`，确认绑定地址、平台端口开放和代理转发；无需开放 Qdrant 端口。
- 503 就绪未通过：等待快照恢复和模型加载，检查磁盘、内存、模型目录及 Qdrant；存活检查成功不代表真实问答可用。
- 模型 API 401/403：核对 `.env` 中供应商、地址、模型、Key 和使用权限；超时检查容器出站网络、额度及平台代理策略。
- GPU 启动失败：先检查驱动和 Container Toolkit，或改用 CPU 启动；CPU 更慢不代表需要下载额外模型。
- 不要混用源码重建入口：提交包默认 Compose 为快照部署，`docker-compose.source.yml` 仅供具备网络的开发人员从 Dockerfile 重建，重建需主动指定 `--platform linux/amd64`。
